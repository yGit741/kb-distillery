# Lifecycle: commits, versions, hygiene

> Lanes, commit formats, versions, hygiene, snapshots/undo, diverged main, nightly schedule, partial checkouts, commit gate. Part of the doc router in [`AGENTS.md`](../../../../../../AGENTS.md).

**Git lifecycle — KB Conventional Commits.** Lane membership lives in `src/kb_distillery/vault/schema.py` (`KNOWLEDGE_PATHS`, `TOOLING_PATHS`, `lane_of`). The dashboard **Lifecycle** tab explains and shows all of it.

| Track | Paths | Committed as | By |
|-------|-------|--------------|----|
| knowledge | `wiki/ think/ raw/ meta/{corpus,coherence-warnings,aliases}.tsv meta/chats/` (`wiki/` holds `index.md` and the `wiki/<type>/index.md` section indexes, generated, and `log.md`, append-only) | `kb(<op>): <summary> (kb-x.y.z)` **directly on main, one commit per operation** — ops: `import catalog digest refine distill think undo restore`; the summary says what was done in words (slugs become words, cut at a word), the body lists the wiki pages touched; trailers `KB-Version KB-Op KB-Target` (a slug, never a hash) (+`KB-Reverts`, `KB-Snapshot`, `KB-Tier easy\|full\|deep` on digests) | writer CLIs (`kb_distillery.ingest`, `kb_distillery.distill`) automatically; free-form wiki edits via `pixi run ops -- begin …` / `commit` (skill `wiki-edit`); your `think/` edits as `kb(think)` before each op and nightly |
| tooling | `meta/` (code, skills, dashboard, docs), `.claude/ .github/`, `pixi.*`, root `*.md`, `.gitignore` | `schema|feat|fix|chore|paradigm(<component>): <imperative summary>` on `infra/<feature>` (scope always required; docs/tests/refactors are `chore`), merged as a merge commit `… (#N)` whose body lists the branch's commits; the title takes the highest type of its commits (paradigm › schema › feat › fix › chore — `ship pr`/`merge` refuse a lower one), whole subject ≤ 100 chars — **never squash**; main is merged into the branch only when it gained more than kb steps | `pixi run ship -- start/commit/pr/merge` (skill `infra-pr`) — whenever the user asks for a fix/change/feature; **the agent merges by default**, a `hold`-labelled PR (schema/paradigm, or `pr --hold`) waits for the user's `ship approve N` |
| other | anything else | never committed — `pixi run lanes` lists it; gitignore, move or delete | — |

**A knowledge base repo's own tooling** (`.claude/` hooks, `CLAUDE.md`, `AGENTS.md`, `.obsidian/`, `.gitignore`, `kb.toml`) is neither knowledge nor engine code: it lands directly on that repo's main as `chore(<scope>): …`, unversioned, and only when every path is one of those (`KB_TOOLING_PATHS` in `src/kb_distillery/vault/schema.py`; the commit-msg hook and the pre-push check enforce it). Any other infra type, or a chore that touches `wiki/`, `raw/` or `think/`, is refused there. The engine repo and the think repo do not get this rule. **Agents commit these with `pixi run ops -- chore <scope> "summary" [paths…]`** (kb repo's main only; it takes just the tooling files, never a knowledge edit sitting in the same tree; `ops migrate` does the same for a schema bump). A raw `git commit` there stays blocked.

**Versions are knowledge-only:** `kb-x.y.z` — x paradigm, y schema (`SCHEMA_VERSION` in `src/kb_distillery/vault/schema.py`), z step (computed). Tooling is unversioned; a `schema`/`paradigm` PR carries its migration (`src/kb_distillery/migrations/`, `pixi run ops -- migrate` on the branch), snapshots first (`pre-<feature>`) and again after the merge (`post-<feature>`, the new baseline) and bumps y/x. Schema 1.0 (the source model, see [`page-model.md`](page-model.md)) was a paradigm PR: kb-1.0.0.

**Diverged main** (two sessions pushed the same pages from different bases): `ops sync` fast-forwards or replays unpushed `kb(...)` steps and aborts on a conflict; only the user's `--prefer local|origin` picks a side (a rebase `-X` strategy, whole conflicting hunks), and `--root` lets a worktree run it against the primary checkout. Generated files are rebuilt by the next lint.

**Hygiene is built in, never a gate:** every `kb(...)` step pushes main right away (`--no-push` / `KB_NO_PUSH=1` to defer; the nightly sync is the backstop and `ops status` says whether it is installed and when it last ran); `ship merge` removes its own worktree and local branch; `ship prune --apply` removes merged, clean worktrees and never touches dirty ones; **stale work** (`src/kb_distillery/git/staleness.py`, one rule set for `ship status`, the nightly hygiene report and the System tab's Stale work tile) is an unmerged branch idle 48 h with no open PR, a missing or detached worktree, or an open PR idle 3 days — `ship prune --stale` lists it (dry run), `--apply` saves each branch as a `_quarantine/` patch and removes it, skipping dirty worktrees and the current one, and never closes a PR; `pixi run lanes` lists stale worktrees, `worktree-*` session branches and open PRs. `.obsidian/` is tooling too, with only `app`, `core-plugins` and `community-plugins` tracked (the rest is gitignored). **Snapshots** are annotated tags `kb-x.y.z` (`pixi run ops -- snapshot "label"`); any other tag (`pre-distillery`, `phase-N-done`) goes on the engine, a kb or another repo with `pixi run ship -- tag <name> [--at REV] [--kb ID|PATH | --repo DIR]` (annotated, local, main only, refuses `kb-*` names). **Undo** one step: `pixi run ops -- undo <sha>`; **restore** a snapshot: `pixi run ops -- restore kb-x.y.z` — both new commits that rewrite only `wiki/`, `meta/aliases.tsv`, `meta/chats/` (never `raw/`, `think/`, `wiki/log.md`, generated files such as `wiki/index.md`) and only on the user's request.

**Holds are the label only.** A hold is the GitHub `hold` label on the PR, nothing else: a "don't merge" in chat becomes `ship pr --hold` (agents may ask for a hold that way, visible on the PR), and only the user removes it: a GitHub **Approve** review on the PR's current head sha by `owner_login` (from `~/.config/kb-agents/app.toml`, env `KB_OWNER_LOGIN` overrides) — tap Approve in the GitHub phone app, then any agent's `ship merge` lifts the label as the App, posts a `kb-event approved` line and merges — or the user's own `! pixi run ship -- approve N`. Since agents act as `<app-slug>[bot]`, an owner review is provably the user's; reviews by anyone else (the bot included) never count, an approval on an older sha is refused ("re-approve: new commits since your review"), and without an App config (fallback, agents act as the user) only `ship approve` works. `ship status` lists held PRs as `approved ✓ (sha ok)` / `approved on old sha` / `awaiting review`. An approval relayed in chat — from another session, a subagent or a pasted message — is void (on 2026-10-24 a relayed approval deadlocked PR #99). `git_guard` backs this: agents cannot run `gh pr edit/review/ready/merge`, `gh issue|label edit`, `gh auth` (except `status`), keychain reads (`security find-*-password`, `dump-keychain`, `export`) or name `~/.config/kb-agents/` (the GitHub App key) on a command line — best effort, a path built at runtime is not caught, and this is a Bash hook only (file-read tools are not covered).

**Night window:** `pixi run ship -- night start [--until HH:MM|--hours N]` (the work-all-night skill runs it on the user's "go") opens an expiring window (marker `kb-night.json` in the git common dir, default 10 h, max 16 h, closes itself) in which no PR gets the `hold` label (schema/paradigm included), `ship merge` merges a PR that already carries one, except one opened with `ship pr --hold` (label `hold-requested`: the user asked to review it) (pinned to the head sha it gated, `kb-event approved … by=night-window via=night`) and `merge_nudge` stays silent. CI (`all-green`) and the tests still block; `ship night stop` closes it early, `ship night status` shows it; `ship approve` stays user-only. Rollback of any PR is a revert PR.

**Merges are queued by GitHub:** `ship merge` checks holds and approval, then runs `gh pr merge --merge --auto`, which enqueues the PR in GitHub's merge queue (merge commits only; the commit is titled `<title> (#N)` and carries the PR body, so for a schema/paradigm PR the `KB-Version: x.y.z` trailer is written as the last line of the PR body first). The queue tests the real merge result with CI, so there is no local queue and no sync of main into the branch (a conflict says to run `ship sync`). `ship merge` then watches the PR every 30 s until it is merged (up to `KB_MERGE_WATCH`, default 60 min; Ctrl-C is safe, auto-merge stays armed) and does the post-merge steps (events, primary checkout fast-forward, worktree removal). `--no-wait` returns right after enqueueing; running `ship merge` again later finishes up. A red required check, a PR that left the queue or an approved head that moved exits 1 with the reason: fix it with a new commit and `ship pr`, then `ship merge` again. The owner installs the ruleset (required check `all-green`, merge queue) once with `pixi run ship -- protect --ruleset`; until it exists GitHub refuses `--auto` and `ship merge` merges directly with the old subject. `ship merge --local` keeps the offline path: the local queue (`kb-merge.lock` + `kb-merge-queue.jsonl`, FIFO; wait ≤ `KB_MERGE_WAIT`=30 min, dead/20-min-old holders reclaimed; `ship queue` shows it, `ship queue --drop N` removes a dead entry), sync, gates here, `merge --no-ff`.

**PR events:** `ship` comments one machine-readable line per lifecycle step on the PR — `kb-event v1 · <event> · <sha7> · <k=v …> · <YYYY-MM-DDTHH:MMZ>` (UTC minute; events `claimed` (on `ship pr`, with `branch=` and touched top-level `dirs=`), `queued`, `checks-passed`/`checks-failed`, `merged` (main sha), `deployed`, `rolled-back`; `kb_distillery.git.events.post`). Posting is best-effort (one retry, never fails ship). Read a PR's state with `ship events N` (parses only `kb-event v1` lines) instead of relayed messages; agents still cannot `gh pr comment` directly.

**Path claims:** `ship start <feature> --paths a/b,c/d` records which paths the branch will touch (git config `branch.infra/<feature>.kbPaths`); `ship pr` writes `Claims: a/b, c/d` into the PR body and `paths=` into the `claimed` event (without `--paths`, the branch's touched dirs). At `start` and again at `pr` the claim is compared — dir-prefix match — with every other lane: open `infra/*` PRs (their `Claims:` line, else their changed files) and local worktrees (their diff vs origin/main plus any stored claim). Overlaps print an `OVERLAP` block (branch, `PR #N title` or worktree, paths) and ship carries on: a warning, never a block — the user decides whether to wait, split or coordinate. A failing `gh` prints a note. `ship claims` lists every lane's paths, one line each (`claims`/`files`/`diff` says where they came from).

**Round issues:** a multi-PR effort opens one GitHub issue labelled `round` — `ship round open "<title>" --features a,b,c` (prints `#R`; body = `<!-- kb-round v1 -->` marker + one `- [ ] <feature>` line each). `ship start <feature> --round R` links the branch (git config `branch.infra/<feature>.kbRound`); `ship pr` writes `Round: #R` at the top of the PR body and posts `claimed` on the issue too; `merged` (and `deployed`, once posted) comments the same kb-event line on the issue with `feature=`/`pr=` and ticks that feature's line (`- [x] <feature> (#N)`). The orchestrator reads the whole effort with `ship round status R` — `done/total`, then one line per feature: checkbox, name, latest event, PR. Best-effort like PR events: a failing `gh issue` call prints a note and never fails ship; agents still cannot `gh issue edit` directly (`gh issue comment` is not guarded yet).

**One deploy owner:** the private site is deployed only by `kb_distillery.publish.cloudflare.owner` (launchd `com.kb-distillery.deploy-owner`, KeepAlive; the user installs it with `pixi run install-deploy-owner`, log `~/Library/Logs/kb-distillery-deploy-owner.log`). It builds each origin/main sha once (`.cache/share/build/<sha>`), uploads + deploys a Worker version, health-checks it and rolls back on failure, posting `deployed`/`rolled-back` events; per-sha state in `.cache/share/owner.json` (`python -m kb_distillery.publish.cloudflare.owner status`). `kb(...)` commits, `ship merge` and the nightly sync only touch `.cache/share/wake`; `KB_SHARE_DIRECT=1` (user only) restores the old direct `deploy-main`. `deploy-main.yml` is the daily fallback and no-ops when the owner deployed in the last 24 h. Agents never deploy or roll back — `.claude/settings.json` denies it.

**Agent identity:** every gh call that `ship`, `events`, `rounds` and `merge_nudge` make runs as the `<app-slug>[bot]` GitHub App (`kb_distillery.git.app_token.run_gh` sets `GH_TOKEN`); `git push` from `ship` goes as the App too when its installation token has `contents: write` (via a `GIT_ASKPASS` script reading an env var — the token is never in `.git/config` or output; a refused push retries with your credentials). Setup: `~/.config/kb-agents/app.toml` (`app_id`, `installation_id`, `slug`, optional `key_path`, default `key.pem` beside it; override the path with `KB_APP_CONFIG`). The code signs a 10-min JWT, mints a 1 h installation token and caches it in `.cache/gh-app-token.json` (mode 600, gitignored, re-minted 5 min before expiry). No config or a failed mint → one warning line and gh uses your own `gh auth` (user fallback). `pixi run ship -- whoami` prints which identity is in use. Agents never read the key file themselves.

**Nightly schedule:** `pixi run install-sync` installs `examples/launchd/com.kb-distillery.daily-sync.plist` into `~/Library/LaunchAgents/` (log: `~/Library/Logs/kb-distillery-daily-sync.log`). It must run on this Mac — a cloud agent can't see local edits. After the sync it runs the hygiene checks (`src/kb_distillery/ops/hygiene.py`) and the open work threads (`src/kb_distillery/ops/threads.py`), mails the nightly report (`src/kb_distillery/ops/nightly_report.py` → `src/kb_distillery/ops/notify.py`, HTML + text; config `meta/ops/sync.toml` — `mode = "digest"` every night, `"problems"` only when something needs fixing; password in the macOS keychain) and logs the run to `meta/.ops/runs.jsonl`; the dashboard **Ops** tab (`/ops`) shows the same live. See the engine guide `docs/guides/run-the-nightly-job.md`.

**Partial checkouts:** raw binaries are gitignored, so a clone, a CI run or a fresh worktree lacks them. Lint detects this (≥5 manifest rows of binaries missing from disk, or `KB_CI=1`) and keeps those rows exactly as committed instead of dropping them; everything on disk reconciles as usual. Fewer missing files count as a deliberate deletion.

**Reviewer pass:** `ship pr` refuses unless the branch's HEAD has a recorded review. Run the read-only `reviewer` subagent (`.claude/agents/reviewer.md`) on the branch, fix its blocking findings, commit, then record the verdict with `pixi run ship -- review --pass "<one-line summary>" [--findings N]` (it stores HEAD's sha per branch in `kb-reviews.json` in the git common dir, `src/kb_distillery/git/review_gate.py`); any later commit makes the record stale and `ship pr` names that command again. The summary goes into the PR body under `## Review`. `ship pr --no-review "<reason>"` bypasses the check and the reason lands in the same section.

**Ship gates:** CI is the gate: `.github/workflows/ci.yml` runs every gate (pytest in 4 shards with `-n auto`, ruff, lint-skills, licenses, lint-imports, lint, okf-check, web-check, the lane checks api-schema-check / flags-check / test-e2e / test-ui-principles in its `checks` job, wheel, worker) on every pull request and every merge-queue group; the one required check is the fan-in job `all-green`. `ship commit` refuses first what needs no gate (policy, nothing to commit, unrelated staged files), then runs only the fast local gates, without the machine-wide gate slot and without the load wait: `ruff`, `lint-imports`, a pytest **subset** with `-n auto` (mirror dirs of the touched `src/kb_distillery/<pkg>`, changed test files, always the top-level `tests/test_*.py` invariants; `pixi.toml`/`pyproject.toml`/`conftest.py` or an unmapped path → full suite) and `web-typecheck` when `web/` changed; target under two minutes. `ship pr` needs the recorded reviewer pass, pushes and opens or updates the PR (retitling it when `--title` is passed); it no longer runs the full gates or the lane checks locally. **`KB_SHIP_LOCAL_GATES=1`** restores the old behaviour in every step (the full gates in the slot at commit, pr, `sync --continue` and merge) for offline work or a CI outage; everything below applies to that mode (`sync --continue` first stages, by itself, every both-sides-edited text file you resolved (no conflict markers left), never a `wiki/`, `raw/` or `think/` path, so no `git add` is needed). A gate or lane check that already passed on the same content is skipped (`gate: <name> reused (<sha7>)`): the key is gate, scope (`full`|`subset`; only the tests gate has a subset), a tree sha taken from a throwaway index (no HEAD, generated files and gitignored files excluded, identical uncommitted or committed), the `$KB` and, for the frontend gates, the gate set; records live in `.cache/ship-gates/reuse/` of the worktree and only a real pass is recorded. A subset pass is never reused by `pr`/`merge`. **One gate run at a time per machine (local-gates mode):** a real gate or check run (never a reused one) first takes `kb-gate.lock` in the git common dir (`src/kb_distillery/git/gate_slot.py`, an `fcntl.flock` shared by every worktree), once for the whole gates-and-checks sequence of a `ship` invocation; a second run prints `gate slot: waiting for <holder>` and then `gate slot: taken (waited Ns)`, gives up after `KB_GATE_WAIT` (default 45 min) with a clear error, and a crashed holder frees it at once (the kernel drops the lock). Lock order is merge slot first, gate slot second, never the reverse; gate children carry `KB_GATE_SLOT_HELD=1` so the test suite never asks for its parent's lock. **Gate budget:** a step runs under a watchdog (`gate_slot.supervise`): no new log output for `KB_GATE_IDLE_MIN` (default 10) minutes with the process tree at ~0% CPU, or more than `KB_GATE_STEP_MAX_MIN` (default 45) in all, kills the tree, frees the slot and fails the step (`hung gate, stopped after N idle minutes`, with the log path); a vitest/e2e step first waits (inside the wait limit) until the 1-minute load average is below `KB_GATE_MAX_LOAD` (default 2x CPU count). Gate vitest runs are capped at 4 workers (`--maxWorkers=4`; `web/vite.config.ts` does the same for `web-check` inside a gate), a developer's own run is not.

**Commit gate:** `scripts/githooks/` (`pixi run install-hooks`): `pre-commit` runs `src/kb_distillery/lint/lint.py` then `src/kb_distillery/lint/okf_check.py` (+ `lint_skills.py` for tooling), `commit-msg` and `pre-push` run `src/kb_distillery/git/commit_policy.py`. **`okf-check` blocks** (no bypass flag): `ops` commits run it right after lint on the pages that commit changes (one bad page never blocks an unrelated step; a commit that fixes it passes; `undo` and `restore` are exempt, they are the way out) and refuse with `okf-check failed — nothing committed` and one `ERROR okf-check: <file>: <rule>: <detail>` line per finding; `ship` gates run it on the whole bundle of `examples/demo`, and `pixi run okf-check` checks a whole kb by hand; the pre-commit hook checks the staged pages. Rules: no parseable `type`, invalid `status`, `sources` entry without `resource`, timestamp without UTC offset, leftover wikilink, unresolved link or anchor, link into `raw/` or `think/`; `wiki/index.md` and `wiki/log.md` are reserved files, not pages (their links are checked, `log.md` may quote old `[[...]]` text). `python3 -m kb_distillery.lint.lint --health` or `pixi run health` for vault health.

**Migrations are all or nothing.** `ops migrate` first runs a preflight on a throwaway copy of the kb (pending migrations, the kb.toml bump, then lint and okf-check on the result). If anything would fail, it refuses before a write or a commit and lists every finding (a kb with unresolved `[[x]]` links fixes them first); `ops migrate --dry-run` prints that list and writes nothing. The real run applies every pending migration, then records the `applied.tsv` rows; if one raises, the kb is put back exactly as it was and nothing is recorded. CRLF pages are migrated and keep their line ends; a page whose line ends cannot be kept stops the run with its name.

## Favorites

A favorite is a binary mark on a wiki page. It lives at the kb level in `meta/favorites.json` (`{"v": 1, "slugs": [...]}`, sorted), not in the page, so it is not a schema change. `pixi run ops -- favorite add|remove <slug>` and `favorite list` (the `/api/favorites` routes call the same code) change it as one knowledge step each (`kb(refine): favorite add <slug> (kb-x.y.z)`, pushed right away); a non-page slug is an error, marking twice or unmarking a missing one is a no-op. **Guard:** every knowledge step (`ops commit`, `ops record`) that deletes a favorite page (a merge, a split that drops the original, a delete, a move away to another name) is refused with `<slug> is a favorite: pass --confirm-favorite to delete it` unless `--confirm-favorite` is given; a confirmed delete drops the slug in the same step, and a rename moves the mark to the new slug. One function, `ops.favorite.apply_to_step` (with `guard`), is called from `core.commit_op`.
